## 一、心智模型：为什么要 JOIN？

**一句话**：因为**信息被分开放了**。

```
现状：你的所有信息都压在一张表里
      订单表：订单编号 日期 商品名称 类别 单价 数量 城市 月份 销售额

问题：想算"毛利润" → 需要【成本价】→ 但订单表里没有成本价！
      因为成本是商品属性，不是订单属性 → 它应该放在另一张表
```

**比喻**：两张 Excel 表拼成一张宽表

```
订单表（40 行）                商品成本表（11 行）
┌──────┬──────┬────────┐     ┌──────┬──────┬────────┐
│商品名 │ 数量 │ 销售额 │     │商品名 │成本价│ 供应商 │
├──────┼──────┼────────┤     ├──────┼──────┼────────┤
│ 樱桃 │  19  │ 1140.0 │     │ 樱桃 │ 42.0 │山野果园│
│ 樱桃 │   4  │  240.0 │     │ 咖啡 │ 22.0 │云南豆业│
└──────┴──────┴────────┘     └──────┴──────┴────────┘
      ↓  JOIN ON 订单.商品名称 = 商品成本.商品名称
┌──────┬──────┬────────┬──────┬────────┐
│商品名 │ 数量 │ 销售额 │成本价│ 供应商 │  ← 拼成宽表
├──────┼──────┼────────┼──────┼────────┤    现在能算毛利润了！
│ 樱桃 │  19  │ 1140.0 │ 42.0 │山野果园│
│ 樱桃 │   4  │  240.0 │ 42.0 │山野果园│  ← 每一行都补上了成本信息
└──────┴──────┴────────┴──────┴────────┘
```

> 🔑 **核心理解**：JOIN 就是**按一个"共同列"（这里是商品名称）**，
> 把右表的列**贴到**左表每一行后面。
>
> **为什么要分表？** 因为成本是"每个商品一份"（11 条），
> 订单是"每笔交易一条"（40 条）。**硬塞进一张表会产生大量重复**——
> 这叫**数据库设计的"规范化"**，是专业做法。

## 二、语法模板

```sql
SELECT 表A.列1, 表B.列2, 聚合函数
FROM 表A
INNER JOIN 表B ON 表A.共同列 = 表B.共同列
WHERE ...
GROUP BY ...
ORDER BY ...
```

**三个要点**：

1. **`ON` 是必须的** —— 告诉 SQL"按什么拼"
2. **写 `表名.列名`** —— 两张表都有 `商品名称` 这一列，不写清楚它会**不知道你说哪个**
3. **`INNER` 可以省略** —— `JOIN` 默认就是 `INNER JOIN`（但写出来更清楚）

## 三、⭐ INNER JOIN vs LEFT JOIN（面试必问）

**区别只有一句话**：

```
INNER JOIN  只保留【两边都匹配上】的行
LEFT  JOIN  保留【左表全部】的行，右表匹配不上的填 NULL
```

**用你的数据看**（这就是练习第 3 题）：

```
订单表 40 行 × 商品成本表 11 行
商品成本表【故意少了薯片、矿泉水】

INNER JOIN → 38 行  ← 薯片、矿泉水那 2 笔订单被【丢掉】了
LEFT  JOIN → 40 行  ← 全部保留，那 2 行成本价显示 NULL
```

**为什么差 2 行**：薯片有 1 笔订单、矿泉水有 1 笔订单，成本表里没有它们 → INNER JOIN 匹配不上 → 丢掉。

### 用哪个？（判断法）

| 需求 | 用哪个 | 理由 |
|---|---|---|
| 只想算 **有成本数据的商品** 的毛利润 | `INNER JOIN` | 没成本的算不了，丢掉合理 |
| 想**检查哪些商品缺成本数据** | `LEFT JOIN` + `WHERE 右表.列 IS NULL` | 要保留缺失的行才能发现它 |
| 想**列出所有订单**（不管有没有成本） | `LEFT JOIN` | 不能丢订单 |

> 🔑 **口诀：`INNER` 只要"配得上"的；`LEFT` 是"左表全都留，配不上就留空"。**

### 💡 LEFT JOIN 最实用的场景：**找缺失数据**

```sql
-- 找出"有订单、但成本表里没有"的商品
SELECT DISTINCT 订单.商品名称
FROM 订单
LEFT JOIN 商品成本 ON 订单.商品名称 = 商品成本.商品名称
WHERE 商品成本.商品名称 IS NULL        -- ← 右表没匹配上 = 缺失
```

**这叫"数据完整性检查"**，真实工作中非常常用：
- 用户表有、订单表没有 → 找"注册了但没下单的人"
- 商品表有、库存表没有 → 找"没录库存的商品"

## 四、用 JOIN 算毛利润（本课核心）

```sql
SELECT 订单.商品名称,
       SUM(订单.销售额) AS 销售额,
       SUM(订单.数量 * 商品成本.成本价) AS 总成本,
       ROUND(SUM(订单.销售额 - 订单.数量 * 商品成本.成本价), 2) AS 毛利润
FROM 订单
INNER JOIN 商品成本 ON 订单.商品名称 = 商品成本.商品名称
GROUP BY 订单.商品名称
ORDER BY 毛利润 DESC;
```

**三个细节**：

1. **`数量 * 成本价`** 要写在 `SUM()` **里面** —— 先算每笔的成本，再求和
   ```
   ✅ SUM(数量 * 成本价)     每笔成本相加
   ❌ SUM(数量) * SUM(成本价)  这是把两个总和相乘 —— 完全不同的（错的）结果
   ```
2. **不要用 `JOIN` 后的 `销售额` 原样求和** —— 见下面第五节的陷阱
3. **`ROUND(..., 2)`** 处理浮点小数（和 Python 的 `round` 同理）

**对账结果**（你能算出来的）：

| 商品 | 销售额 | 总成本 | 毛利润 |
|---|---|---|---|
| 樱桃 | 3240.0 | 2268.0 | **972.0** |
| 咖啡 | 2170.0 | 1364.0 | **806.0** |
| 西瓜 | 855.0 | 541.5 | **313.5** |
| 巧克力 | 775.0 | 527.0 | 248.0 |

## 五、⚠️⚠️ JOIN 的经典陷阱：行数变多，数字虚高

**这是数据分析中最常见的错误之一，必须知道。**

```
如果右表对同一个"商品名称"有【多行】（比如不同供应商的报价），
那么 JOIN 之后，左表的 1 行会变成 N 行 → 销售额被【重复计算】！
```

**举例说明**：

```
左表：樱桃 1 笔订单，销售额 1140
右表：樱桃 有 2 条成本记录（A供应商 42 元、B供应商 45 元）

JOIN 后：
  樱桃 | 1140 | A供应商
  樱桃 | 1140 | B供应商     ← 这一行是"多出来的"
→ SUM(销售额) = 2280 ❌ 虚高一倍！
```

**本课的 `商品成本` 表设计成"每个商品只有 1 行"**，所以是**多对一**关系，JOIN 后行数不变（40 → 38，只少了缺失的 2 笔），**不会踩这个坑**。

> 🔑 **但真实数据里经常有这种情况，所以铁律是：**
> **JOIN 之后，先看行数对不对，再算数字。**
> **`INNER JOIN` 后行数变了（变多）→ 说明右表有重复的匹配键 → 要先去重或换连接方式。**

**自查动作**：写完 JOIN，先跑一个 `COUNT(*)` 看看行数合不合理。

## 六、⭐ 本课真实发现：一个你第 6 周漏掉的脏数据

**练习第 7 题**会让你发现：

```
商品名称 | 类别数 | 类别列表
巧克力   |   2    | 零食,水果     ← 同一个商品，两个类别！
```

**具体是哪一笔**（练习第 8 题）：

```
订单编号 | 商品名称 | 类别 | 单价 | 数量
ORD0011 | 巧克力 | 零食 | 25.0 | 3
ORD0024 | 巧克力 | 零食 | 25.0 | 19
ORD0029 | 巧克力 | 水果 | 25.0 | 1     ← ⚠️ 这一笔错标了
ORD0044 | 巧克力 | 零食 | 25.0 | 8
```

**单价都是 25.0**，说明是同一个商品 → `ORD0029` 的类别标错了。

### 💡 这件事的三个意义

**① 你第 6 周的数据清洗漏了一类检查**

```
你当时查了：重复行 / 缺失值 / 多余空格 / 负数量0单价 / 日期格式
但没查：    【同一个实体是否被标成多个类别】
```

> 🔑 **补进你的"数据清洗六件套"**：
> ```python
> # 新增第六件：一致性检查
> df.groupby("商品名称")["类别"].nunique() > 1    # 同一商品多个类别
> ```

**② 它的代价是真实的：两个类别的数字都错了**

```
巧克力 那笔错标订单：销售额 25.0 - 数量1 × 成本17.0 = 毛利润 8.0
→ 这 8.0 被算进了「水果」而不是「零食」

修复前：水果 1425.1 / 零食 366.0
修复后：水果 1417.1 / 零食 374.0   ← 各错了 8.0
```

**你第 6 周报告里的「水果 4502.1」「零食 1206.8」也受同一个错误影响**（差 25 元销售额）。

**③ 修复它需要 `UPDATE`（新语法）**

```sql
UPDATE 订单 SET 类别 = '零食' WHERE 订单编号 = 'ORD0029'
```

**⚠️⚠️ `UPDATE` 的两个安全铁律**：

```
① 【必须先查后改】
   先 SELECT 看一眼要改哪些行，确认无误再 UPDATE
   —— 这是真实工作的安全习惯（改错数据很难恢复）

② 【绝不能忘 WHERE】
   UPDATE 订单 SET 类别 = '零食'          ← 会把【全表 40 行】的类别都改成"零食"！
   UPDATE 订单 SET 类别 = '零食' WHERE 订单编号 = 'ORD0029'   ← 只改 1 行
```

**以及一个 Python 相关的点**：

```python
# ⚠️ 改动数据的语句，必须 commit，否则程序一关就没了
cursor.execute("UPDATE ...")
conn.commit()      # ← 少了这行，改动白做
```

> 练习文件里的 `show()` 已经支持 `commit=True` 参数：
> `show("""UPDATE ...""", "标题", commit=True)`

## 七、打通 Python：`pandas.read_sql()`

**这是本课最后一环，也是最实用的一环。**

```python
import pandas as pd
import sqlite3

conn = sqlite3.connect("销售.db")

df = pd.read_sql("""
    SELECT 订单.商品名称, ROUND(SUM(订单.销售额 - 订单.数量*商品成本.成本价),2) AS 毛利润
    FROM 订单 INNER JOIN 商品成本 ON 订单.商品名称 = 商品成本.商品名称
    GROUP BY 订单.商品名称
""", conn)                    # ← 注意：传的是 conn（连接），不是 cursor

print(df.head())
print(df["毛利润"].sum())
```

### 为什么这个函数重要

```
真实工作的数据链路：

  数据库（可能有几千万行）
      ↓ SQL 负责【取数】（只把要的那部分捞出来，快！）
  pandas.read_sql()
      ↓ DataFrame
  Pandas 负责【分析 / 清洗 / 计算】
      ↓
  Matplotlib 负责【画图】
      ↓
  出报告 / 出结论
```

> 🔑 **分工口诀：SQL 取数，Pandas 分析，Matplotlib 出图。**
> **不要用 Pandas 去读整张千万行的表**——那会把内存撑爆。
> **该用 SQL 先筛/聚合，再用 Pandas 处理。**

**对比一下**：

| 做法 | 什么时候用 |
|---|---|
| `pd.read_csv()` | 数据在**文件**里 |
| `pd.read_sql()` | 数据在**数据库**里 ⭐ 真实工作更常见 |

## 八、和 Pandas 对照

| 我想干的事 | SQL | Pandas |
|---|---|---|
| 内连接 | `INNER JOIN 表B ON A.键 = B.键` | `pd.merge(df1, df2, on="键", how="inner")` |
| 左连接 | `LEFT JOIN 表B ON A.键 = B.键` | `pd.merge(df1, df2, on="键", how="left")` |
| 找右表缺失 | `LEFT JOIN ... WHERE B.键 IS NULL` | `df1.merge(df2, how="left")` 后筛 `NaN` |
| 从数据库读表 | `SELECT * FROM 表` | `pd.read_sql("SELECT * FROM 表", conn)` |

## 九、本课口诀

```
信息分开放，需要就连表；
JOIN 要写 ON，连接靠共同列；
两张同名列，前面加表名（订单.商品名称）；

INNER 配得上才留，LEFT 左表全都留；
配不上就填 NULL —— 所以能"找缺失"；
LEFT JOIN + IS NULL，找主表有、附表没有的；

毛利润 = 销售额 - 数量 × 成本价；
乘法写在 SUM 里面，别把两个总和乘；

⚠️ JOIN 后先看行数，再看数字对不对；
右表有重复键 → 行数变多 → 销售额虚高；

UPDATE 必须先查后改，绝不能忘 WHERE；
改完必须 commit，不 commit 白改一场。
```

### 坑 C：题 4 少了 `DISTINCT`（题目明确要求"去重"）

```sql
你写的：select 订单.商品名称 from 订单 left join ... where 商品成本.商品名称 is null
应该是：select DISTINCT 订单.商品名称 ...
```

**验证结果**：
```
不加 DISTINCT → 2 行：['矿泉水', '薯片']

**为什么恰好一样**：薯片、矿泉水**各只有 1 笔订单**，不会重复。

> 🔑 **这是"结果对 ≠ 按要求写对"的又一例**（第 2 课的排序方向同类）。

```

**这次恰好没有浮点尾巴**（误差在这个组合下抵消了）。**但题 1 里你就见过 `54.400000000000006`。**

> 🔑 **习惯：凡是带小数的聚合结果，都套 `ROUND(..., 2)`。别赌"这次没尾巴"。**

### 🔬 本课新学到的"自查神器"：**交叉验证**

**题 10 的错本来你自己就能抓出来**：

```
题 2 输出：  西瓜 313.5
题 10 输出： 西瓜 314.0
              ↑ 同一份数据、同一个查询，两个数字不一致！
```

> 🔑 **同一个查询在两处跑出不同结果 → 一定有一处错了。**
> 这在真实工作里叫**交叉验证**，是最有效的自查手段之一。
>
> **这也正是你在第 6 周做过的事**——你用 Pandas 算出"2月客单价 167.6"，
> 这次又用 SQL 验证了一遍，两个结果一致 → 互相印证。
> **"交叉验证"这个习惯，比任何单个技能都值钱。**

### 本课数据状态提醒（实操性坑）

**题 8 会真的修改数据库**（`UPDATE` + `commit`）。所以：

```
第一次跑文件：题6 显示修复前（水果 1425.1）→ 题8 修复 → 题9 显示修复后（1417.1）✅
第二次跑文件：题6 也显示修复后（1417.1）⚠️  → 和平常的"对账目标"对不上
             题7 显示【0 行】（问题已被修复，查不到了）
```

**这不是你写错了**——是**数据已经变了**。

> 🔑 **重要认知：同一句 SQL，数据变了，结果就变了。**
> **"证据"不是 SQL 本身，而是"SQL + 当时的数据状态"。**
>
> 真实工作里的意义：你昨天报表显示"水果赚 1425"，今天重跑变 1417，
> **不是 SQL 坏了，是底层数据被改了** → 所以分析报告必须**注明数据截止时间**。

### 第 3 课总口诀（避坑版）

```
JOIN 要写 ON，连接靠共同列；两张同名列，前面加表名；
INNER 配得上才留，LEFT 左表全都留，配不上填 NULL；
LEFT JOIN + IS NULL，专找"主表有、附表没有"的；

乘法写在 SUM 里面，别把两个总和乘；
⚠️ JOIN 后先看行数，再看数字对不对；

UPDATE 先查后改，绝不能忘 WHERE；改完必须 commit；
改了数据，同一句 SQL 的结果就变了 —— 报告要注明数据时间；

ROUND 结尾看三个字符：必须是 ", 2)"  —— 这个错我犯了 2 次；
带小数的聚合都套 ROUND，别赌"这次没尾巴"；
DISTINCT、排序方向 —— 写完回头看题目，问"我用什么保证了它"；

head() 只能看大概，验证要看全量或汇总；
同一个查询两处跑出不同数 → 一定有一处错了（交叉验证）。
```
