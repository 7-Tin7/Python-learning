# 第 6.5 单元 · 第 2 课：聚合与分组（GROUP BY）

> 素材：还是那 40 行销售数据（`销售.db` 表【订单】）
> 目标：会写 `COUNT / SUM / AVG / MAX / MIN / GROUP BY / HAVING`
> 特点：**学完这节课，你能用 SQL 把你第 6 周分析报告的数字全部重算一遍**

---

## 一、心智模型：从"行"到"堆"（本课最重要的一步）

**第 1 课**你学的是**挑行**（WHERE）——一行一行看明细。
**第 2 课**要学的是**分堆**——把行按某个标准分成几堆，然后**每堆压成一个数**。

```
比喻：一堆混在一起的衣服
         ↓ 按类别分堆（GROUP BY 类别）
   [上衣堆]   [裤子堆]   [袜子堆]
         ↓ 每堆各算一遍（聚合函数）
   数件数(COUNT) / 称总重(SUM) / 平均重(AVG)

对应到数据：
   40 行订单  → 按【类别】分堆 → 水果堆20行 / 饮料堆9行 / 零食堆7行 / 蔬菜堆4行
                              → 每堆的 SUM(销售额) = 4502.1 / 2298.2 / 1206.8 / 141.5
```

> 🔑 **关键区别**：
> `WHERE` 的输出**还是行**（明细）；`GROUP BY` 的输出**是堆**（每个组变成一行）。
> 所以 `GROUP BY` 之后，行数从 40 行变成了 4 行——**信息被"压缩"了，这就是汇总。**

## 二、聚合函数（5 个）

**"聚合" = 把一堆值压成一个值。**

| 函数 | 作用 | 例子 |
|------|------|------|
| `COUNT(*)` | 数有多少行 | `COUNT(*)` → 40 |
| `SUM(列)` | 求和 | `SUM(销售额)` → 8148.6 |
| `AVG(列)` | 求平均 | `AVG(销售额)` → 203.715 |
| `MAX(列)` | 最大值 | `MAX(销售额)` → 1140.0 |
| `MIN(列)` | 最小值 | `MIN(销售额)` → 6.4 |

**单独用**（不配 GROUP BY）= 把**整张表**压成一个数：

```sql
SELECT COUNT(*) AS 订单数,
       SUM(销售额) AS 总销售额,
       ROUND(AVG(销售额), 2) AS 平均客单价
FROM 订单;
-- 结果：40 | 8148.6 | 203.72
```

> `ROUND(值, 位数)` 是四舍五入，和 Python 的 `round()` 一个意思。
> 💡 **注意**：这里的 `AVG(销售额)` **就是客单价**。
> 自己写 `SUM(销售额) / COUNT(*)` 结果也一样（203.715）——
> 因为 `销售额` 是**小数类型**，相除不会丢小数。
> 但换成两个整数相除就要小心了，见第八节坑 1。

## 三、GROUP BY：分堆

```sql
SELECT   类别, SUM(销售额)      -- ① 要【分组列】+【聚合函数】
FROM     订单
GROUP BY 类别                    -- ② 按哪一列分堆
ORDER BY SUM(销售额) DESC;       -- ③ 排个序（可选）
```

**格式模板**：

```
SELECT 分组列, 聚合函数(列)  FROM 表  GROUP BY 分组列  ORDER BY ... LIMIT ...
```

读法："**按什么分组，就对哪列做什么统计**"——和 Pandas 的 `groupby("类别")["销售额"].sum()` 完全同构。

### ⚠️⚠️ 铁律：`SELECT` 后面只放【分组列】和【聚合函数】

```sql
✅ SELECT 类别, SUM(销售额) FROM 订单 GROUP BY 类别;
❌ SELECT 类别, 商品名称, SUM(销售额) FROM 订单 GROUP BY 类别;
```

第二条错在哪？`商品名称` 既不是分组列、也没被聚合——**水果堆里有 20 个商品名，你让 SQL 显示哪一个？**

**最阴险的是：SQLite 不报错！** 它会随便挑一个给你：

```
类别   | 商品名称 | SUM(销售额)
水果   | 樱桃     | 4502.1      ← 樱桃只是"碰巧被挑中的那个"
蔬菜   | 白菜     | 141.5
零食   | 饼干     | 1206.8
饮料   | 可乐     | 2298.2
```

**看起来像正常结果，其实是错的。** 这比报错危险 10 倍——因为你不会去查。

> 🔑 **铁律：不报错 ≠ 对。** 看到"分组统计"的结果，先回头检查 `SELECT` 里有没有混进**非分组列**。

### 💡 顺便一个观察：GROUP BY 不保证顺序

对比上面两次输出：一次是"水果/蔬菜/零食/饮料"，一次是"水果/零食/饮料"——
**顺序是随机的，不按字母、也不按数据先后。**
**要确定的顺序，必须显式写 `ORDER BY`。**

## 四、AS 别名：给算出来的列起名

```sql
SELECT 类别, SUM(销售额) AS 总额 FROM 订单 GROUP BY 类别 ORDER BY 总额 DESC;
```

不加 `AS` 时，列名会显示成难看的 `SUM(销售额)`。加了 `AS 总额` 就清爽了，**而且排序时能直接写 `ORDER BY 总额`**，不用把那串长表达式再抄一遍。

> ⚠️ **跨数据库提醒**：别名用在 `ORDER BY` 里是通用写法（安全）。
> 别名用在 `HAVING` 里，**SQLite 允许，但 MySQL 等标准 SQL 不允许**。
> 面试或换数据库时，`HAVING` 里写**完整表达式**最保险：
> `HAVING SUM(销售额) > 1000`

## 五、`HAVING` vs `WHERE` ⭐ 面试高频考点

这是本课**唯一一个真正的新概念**，也是面试最爱问的。

```sql
-- 需求一：只看【不是未知城市】的订单，再按城市汇总
SELECT 城市, SUM(销售额) FROM 订单
WHERE 城市 != '未知'          -- ← 筛【行】
GROUP BY 城市;

-- 需求二：只看【销售额合计超过 1000】的类别
SELECT 类别, SUM(销售额) FROM 订单
GROUP BY 类别
HAVING SUM(销售额) > 1000;    -- ← 筛【堆】
```

| | `WHERE` | `HAVING` |
|---|---|---|
| **筛什么** | **行**（明细） | **堆**（分组后的结果） |
| **写在哪** | `GROUP BY` **前面** | `GROUP BY` **后面** |
| **能用聚合函数吗** | ❌ 不能 | ✅ 能 |

### 为什么 `WHERE` 不能筛合计？

**因为执行有先后**：`WHERE` 在"分堆之前"就要筛完，可那时候**合计根本还不存在**，你没法拿一个还没算出来的数字做条件。

真试着写会直接报错（我跑过）：

```sql
❌ SELECT 类别, SUM(销售额) FROM 订单 WHERE SUM(销售额) > 1000 GROUP BY 类别;
   -- sqlite3.OperationalError: misuse of aggregate: SUM()
   -- 翻译："SUM() 用错地方了"
```

> 🔑 **口诀：`WHERE` 管分堆前，`HAVING` 管分堆后。**
> **记忆钩子**：`HAVING` 里带**聚合函数**（SUM/COUNT/AVG）→ 那就是它；不带聚合、纯筛明细 → 用 `WHERE`。

## 六、和 Pandas 对照表

| 我想干的事 | SQL | Pandas |
|-----------|-----|--------|
| 整张表求和 | `SELECT SUM(销售额) FROM 订单` | `df["销售额"].sum()` |
| 整张表求平均 | `SELECT AVG(销售额) FROM 订单` | `df["销售额"].mean()` |
| 整张表数行数 | `SELECT COUNT(*) FROM 订单` | `len(df)` |
| 按类别求和 | `SELECT 类别, SUM(销售额) FROM 订单 GROUP BY 类别` | `df.groupby("类别")["销售额"].sum()` |
| 按类别多个统计 | `SELECT 类别, COUNT(*), SUM(销售额) FROM 订单 GROUP BY 类别` | `df.groupby("类别")["销售额"].agg(["count","sum"])` |
| 按类别求和后排序 | `... GROUP BY 类别 ORDER BY SUM(销售额) DESC` | `....sum().sort_values(ascending=False)` |
| 筛合计 | `... GROUP BY 类别 HAVING SUM(销售额) > 1000` | `s = ....sum()` 然后 `s[s > 1000]` |
| 想变回平表 | SQL 结果天然是平表 ✅ | 要 `.reset_index()` |

> 💡 **感受一下**：Pandas 里"筛合计"要**先存成变量再筛**（两步）；
> SQL 里 `HAVING` **一句话就到位**。这就是 SQL 为"汇总查询"而生的地方。

## 七、完整书写顺序（第 2 课版）

```sql
SELECT   列 / 聚合函数
FROM     表
WHERE    行条件          ← 筛行（可选）
GROUP BY 分组列          ← 分堆
HAVING   堆条件          ← 筛堆（可选）
ORDER BY 排序            ← 排序（可选）
LIMIT    行数;           ← 限量（可选）
```

**口诀（按这个顺序背）**：

```
选 → 从 → 行筛 → 分堆 → 堆筛 → 排序 → 限量
```

⚠️ 顺序写错就报错。最常见的两个错：
- `WHERE` 写在 `GROUP BY` **后面** → 错
- `HAVING` 写在 `GROUP BY` **前面** → 错

## 八、⚠️ 三个坑（都真跑过，不是吓你）

### 坑 1：整数除法 —— 算占比算出个 `0`

**SQL 里两个整数相除，结果还是整数，小数部分直接丢掉。**

```
算"水果单数占总单数的比例"（20 ÷ 40 = 0.5）：

❌ COUNT(水果)... / COUNT(*)            →  0        ← 不是 0.5，是 0！小数被丢了
✅ 100.0 * COUNT(水果)... / COUNT(*)     →  50.0     ← 乘个 100.0 就对了
```

#### ⚠️ 最坑的地方：它不是"总是错"，而是"除不尽的时候才悄悄错"

```
100 * 20 / 40    →  50    ← 2000 ÷ 40 正好整除，没小数可丢 → 看起来完全正常！
20 / 40          →  0     ← 0.5 除不尽 → 小数被丢 → 变成 0
100 * (20/40)    →  0     ← 加了括号，计算顺序变了 → 陷阱又冒出来了
```

> 🔑 **同一个写法，有的题对、有的题错**——这就是它最阴的地方。
> （没报错、结果也"长得像对的"，你根本不会怀疑。）

#### 🔑 怎么判断会不会中招？（看除号两边有没有"小数"）

**规则：只要有一边是小数（REAL），除法就走小数运算，安全；
两边都是整数（INTEGER / 整数常量），除不尽就丢小数。**

| 写法 | 两边类型 | 结果 | 真值 | 安全吗 |
|------|---------|------|------|--------|
| `SUM(销售额) / COUNT(*)` | REAL ÷ INTEGER | `203.715` | 203.715 | ✅ 安全（销售额是小数列）|
| `AVG(销售额)` | 内置聚合 | `203.715` | 203.715 | ✅ 安全 |
| `100 * 20 / 40` | 整数 ÷ 整数 | `50` | 50 | ✅ 正好整除（**运气好**）|
| `100 * (20 / 40)` | 整数 ÷ 整数 | `0` | 50 | ❌ **中招**（顺序一变就完）|
| `20 / 40` | 整数 ÷ 整数 | `0` | 0.5 | ❌ **中招** |
| `COUNT(*) / COUNT(*)` | 整数 ÷ 整数 | `1` | 1 | ⚠️ 同表自除正好是 1（**别被这种巧合骗了**）|
| `SUM(数量) / COUNT(*)` | 整数 ÷ 整数 | `10` | **10.725** | ❌❌ **最阴险**，见下 |

#### ❌❌ 最阴险的一种：错得看不出来

```
SUM(数量) / COUNT(*)   →   10        ← 看起来完全合理："平均每单 10 件"
真实值                  →   10.725    ← 429 ÷ 40，那个 .725 被悄悄丢了
```

**对比一下危险程度：**

| 得到的结果 | 你的反应 | 危险度 |
|-----------|---------|--------|
| `0`（本应 0.5）| "咦怎么会是 0？肯定有 bug" → 会去查 ✅ | 低 |
| `10`（本应 10.725）| "平均 10 件，合理" → **直接拿去汇报** ❌ | **高** |

> 🔑 **记住这条**：整数除法最可怕的不是算出 `0`（那个你会怀疑），
> 而是算出一个**看起来完全合理的整数**——你根本不会去查。

> **记忆法**：`销售额` `单价` 是小数列 → 除着放心；
> `数量` `月份` 和 **`COUNT(*)`** 都是整数 → **想算比例，先乘 `1.0`**。
>
> **铁律：算"占比/比例"时，主动写 `100.0 *` 或 `1.0 *`。别赌"这次能整除"。**
> 这和 Python 3 的 `/` 不一样（Python 的 `/` 永远给小数）——
> **语言规矩不同，别混着套。**

> 📌 **编者注（真实事故，值得一读）**
>
> 这节笔记的第一版里，老师犯了**三个**错，全被学员自己验证后抓了出来：
>
> ① 自测题 `SELECT 100 * 20 / 40` 的答案写成 `0`（正确是 `50`，因为正好整除）；
> ② 练习题里写"自己写 `总额/单数` 可能会得到 0"（错，`销售额` 是小数列，安全）；
> ③ 本表格里把 `COUNT(*) / COUNT(*)` 标成"结果 0"，实际是 `1`。
>
> 三个错都是**同一类毛病**：讲的人凭印象写，没有真跑一遍。
>
> **教训（对老师和学员都成立）：
> 任何数字、任何结论，跑一遍才算数。老师写的也一样。**
>
> 顺带，这也是"整数除法"这个坑最好的注脚——
> **连专门讲它的人都会连续搞错三次**，可见它有多容易骗过眼睛。

## 九、本课口诀

```
聚合五兄弟：COUNT 数、SUM 加、AVG 平均、MAX/MIN 找两头；

GROUP BY 来分堆，堆完每堆压一个数；
SELECT 只放两样：分组列 + 聚合函数；
不报错 ≠ 对，混进普通列最危险；
分组完顺序是乱的，要顺序必须 ORDER BY；

WHERE 管分堆前，HAVING 管分堆后；
HAVING 带聚合，WHERE 筛明细；
选从行筛分堆堆筛排限量，顺序一乱就报错；

整数相除丢小数，想留小数乘 1.0。
```

8. `GROUP BY 类别` 的结果，顺序是固定的吗？

10. 报错 `misuse of aggregate: SUM()` 通常是什么原因？

<details>
<summary>点开看答案</summary>

1. `COUNT(*)` 数**所有行**（40）；`COUNT(城市)` 数**城市列不为空的行**
   （如果有 NULL 会被跳过）。本例中城市已用"未知"填充过，所以都是 40。
2. `SELECT 城市, SUM(销售额) FROM 订单 GROUP BY 城市 ORDER BY SUM(销售额) DESC`
3. 因为一个组（比如"水果"）里有 20 个商品名，聚合后每堆只剩一行，
   没法决定显示哪一个。SQLite 会随便挑一个 —— **不报错但结果是错的**。
4. 用 `HAVING`。因为"合计"是**分组之后**才算出来的，`WHERE` 执行在分组之前，
   那时合计还不存在（写 `WHERE SUM(...)` 会报 `misuse of aggregate`）。
5. `WHERE` 先执行（先筛行，再分堆）。书写时 `WHERE` 在 `GROUP BY` **前面**。
6. 结果是 `50` —— 因为 `100 × 20 = 2000`，`2000 ÷ 40` **正好整除**，
   整数除法没丢掉任何东西。想得到 `50.0`：写成 `100.0 * 20 / 40`
   （让其中一个数先变成小数）。
   ⚠️ 别被"整数除法"骗了：它**只在除不尽的时候**才丢小数。
   `20 / 40` 会变成 `0`，`100 * (20/40)` 也会变成 `0`——
   所以**不能靠"这次运气好整除"过关，要养成主动写 `1.0` 的习惯**。
7. 该类别的**平均客单价**（每笔订单的平均金额）——你第 6 周报告里
   "2 月客单价 167.6"就是这么来的。
8. 不固定。`GROUP BY` 不保证顺序，要确定顺序必须显式写 `ORDER BY`。
9. `HAVING`。
10. 把聚合函数写进了 `WHERE`（应该写在 `HAVING` 里）。

## 十一、第 2 课实战避坑记录（做完 9 题后总结）

**战绩**：9 题全部做对 ✅（含 1 道挑战题）
**但**：过程中改了两轮。第一轮有 3 题出错、第二轮的 3 题结果不对。
**而且第二轮的 3 个错，根因是同一个。**

### 坑 A：`ROUND` 括号没闭合，`2` 放错了层

```sql
❌ round(avg(销售额,2) as 平均客单价      -- near "as": syntax error
✅ round(avg(销售额), 2) as 平均客单价
```

**括号检查**：左括号 4 个、右括号 3 个 → 差 1 个。
**概念错误**：`2` 成了 `AVG` 的第二个参数（`AVG` 只要一个参数）。

> 🔑 **口诀：`ROUND` 管四舍五入，`AVG` 只算平均——`2` 是给 `ROUND` 的。**
> **自查动作**：写完数一遍括号，每个 `(` 都要有 `)`。

### 坑 B：`DESC` 拼成 `DSEC`（老坑家族第 N 次）

```sql
❌ order by 销售额 DSEC     -- near "DSEC": syntax error
✅ order by 销售额 DESC
```

> 🔑 家族史：`uft-8` → `--online` → `tow` → `form` → **`DSEC`**
> **全是"字母顺序颠倒"**。这类错跑一遍就能发现——**所以写完必须自己跑**。

### 坑 C：⭐ 忘了把【分组列】放进 `SELECT`（**不报错，但结果没用**）

```sql
❌ select sum(销售额),count(*) from 订单 group by 类别
   → 跑出来是：(4502.1, 20) (141.5, 4) (1206.8, 7) (2298.2, 9)
   → ⚠️ 数字都对，但【没有类别名】→ 4502.1 是哪一类？不知道！

✅ select 类别,sum(销售额),count(*) from 订单 group by 类别
```

**这正是第三节标为「⚠️⚠️ 铁律」的那条**：

> `SELECT` 后面只放【分组列】和【聚合函数】

**只做了后半句、漏了前半句。** 而且这个错 **SQLite 不报错**——
照样给你 4 行数据，你说不定就直接拿去汇报了。

> 🔑 **自查动作**：写完任何带 `GROUP BY` 的 SQL，回头看一眼 `SELECT`——
> **第一个位置应该是分组列。**

### 坑 D：⭐ `ORDER BY` 不写方向 = 默认从小到大（最阴的坑）

```sql
❌ order by 销售额合计 limit 3
   → 拿到的是【最低的 3 个】：矿泉水 22 / 西红柿 43.2 / 白菜 57.5
   → 而题目要的是【最赚钱的 3 个】：樱桃 3240 / 咖啡 2170 / 西瓜 855

✅ order by 销售额合计 DESC limit 3
```

**SQL 不写方向不报错，静静给你从小到大。** 你以为取了"前 3 名"，
其实取了"倒数前 3 名"。

> 🔑 **铁律：`ORDER BY` 不写方向 = 默认 ASC（从小到大）。**
> **"前 N 名""最赚钱""最高的""降序" → 必须写 `DESC`。**
> **自查动作**：写完 `ORDER BY` 问自己一句——
> **"我要的是最大的还是最小的？"**

### 坑 E：题目明说"升序"，却写了 `DESC`（漏读要求）

```sql
题目原文："按【月份升序】"
❌ order by 月份 DESC      → 3, 2, 1
✅ order by 月份           → 1, 2, 3
```

数据全对，只是方向反了。
> 🔑 这是"**半份作业**"老毛病的重现：题目给了要求，只做了一半。
> **自查动作**：写完回头看题目，逐项打勾（要哪几列 / 什么条件 / 怎么排）。

### 坑 F：`HAVING` 里用别名 —— SQLite 能跑，但**不可移植**

```sql
你的写法（SQLite ✅，MySQL ❌）：
  select 类别, sum(销售额) as 销售额合计 ... having 销售额合计 > 1000

跨数据库都安全的写法：
  ... having sum(销售额) > 1000        ← 写完整表达式
```

> 🔑 不是错，是**可移植性差异**。面试或换数据库时写完整表达式最保险。

### ⭐ 本课最大收获：三类错，一个共同点

| 坑 | 类型 | 报不报错 |
|---|---|---|
| A 括号 | 语法 | ✅ 报错（好发现）|
| B 拼写 | 语法 | ✅ 报错（好发现）|
| C 缺分组列 | **逻辑** | ❌ **不报错，结果没用** |
| D 排序方向 | **逻辑** | ❌ **不报错，结果错** |
| E 漏读要求 | **逻辑** | ❌ **不报错，结果错** |

> 🔑🔑 **5 个坑里，3 个不报错。**
> **"能跑通" ≠ "结果对"** —— 这是本课最值钱的一条。
> **所以每次跑完，不能只看"有没有报错"，还要看"数字对不对"。**

### 第 2 课总口诀（避坑版）

```
ROUND 管四舍五入，AVG 只算平均；
括号数一遍，左开右要闭；

DESC 不是 DSEC，跑一遍就知道；
分组列放第一个，SELECT 别忘了；

ORDER BY 不写方向，默认从小到大；
要"前N名"就写 DESC，问自己一句"要大的还是小的"；

题目要求逐项对，别做半份作业；
能跑通不等于结果对 —— 跑完还得看数字。
```
