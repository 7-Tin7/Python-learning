一、SQL 基础查询（第 1 课）
────────────────────────────────────────

【1.1 书写顺序（背下来，顺序不能乱）】
  SELECT  列         ← 要哪些列
  FROM    表         ← 从哪张表
  WHERE   条件       ← 只要哪些行
  ORDER BY 列 DESC   ← 按什么排（DESC 大到小，默认 ASC 小到大）
  LIMIT   行数;      ← 最多几行

  【口诀】选 → 从 → 行筛 → 排序 → 限量

【1.2 比较运算符】
  =            等于 ⚠️ 是【一个】=，不是 Python 的 ==
  !=  或  <>   不等于（两种写法都行）
  >   >=   <   <=
  ⚠️ 文字值必须用【单引号】：'深圳'
  ⚠️ 数字不加引号：数量 > 5
  ⚠️ 双引号在 SQL 里是给"列名/表名"用的，写文字会报错

【1.3 AND / OR 与优先级 ⭐ 面试高频】
  AND 比 OR 先算（像"先乘除后加减"）
  ❌ WHERE 城市='上海' OR 城市='深圳' AND 销售额>200
     → SQL 理解成：城市='上海' OR (城市='深圳' AND 销售额>200)
     → 8 行（混进了 31.5 的小额上海单，不符合要求）
  ✅ WHERE (城市='上海' OR 城市='深圳') AND 销售额>200
     → 4 行（正确）
  【口诀】AND 咬得紧，OR 松；要改先后，上括号。
  【铁律】WHERE 里同时有 AND 和 OR → 先想"要不要括号"，不确定就加

【1.4 实战对账数据（可用来自查）】
  数据：表【订单】40 行（来源：第 6 周清洗后的销售数据）
  SELECT * FROM 订单 LIMIT 5            → 5 行
  SELECT 商品名称, 销售额 FROM 订单       → 40 行
  WHERE 城市 = '深圳'                    → 8 行
  WHERE 数量 >= 5 AND 类别 = '饮料'       → 8 行
  ORDER BY 销售额 DESC LIMIT 3           → 樱桃1140 / 樱桃780 / 咖啡700
  SELECT COUNT(*) FROM 订单              → 40

二、聚合与分组（第 2 课）⭐ SQL 的分水岭
────────────────────────────────────────

【2.1 思维转变：从"行"到"堆"】
  第 1 课 WHERE     → 一行一行【挑】明细（输出还是行）
  第 2 课 GROUP BY  → 把行【分堆】，每堆压成一个数（输出变成"堆"）

  比喻：一堆混着的衣服 → 按类别分堆 → 每堆数件数、称总重
  40 行订单 → 按类别分堆（水果20/饮料9/零食7/蔬菜4）→ 每堆求 SUM

【2.2 聚合函数（5 个）】
  COUNT(*)   数有多少行        SUM(列)   求和
  AVG(列)    求平均            MAX(列)   最大     MIN(列)   最小

  单独用 = 整张表压成一个数：
  SELECT COUNT(*) AS 订单数, SUM(销售额) AS 总销售额,
         ROUND(AVG(销售额), 2) AS 平均客单价
  FROM 订单;
  -- 结果：40 | 8148.6 | 203.72

【2.3 分组模板】
  SELECT 分组列, 聚合函数(列) AS 别名
  FROM 表
  WHERE 行条件            ← 筛【行】（可选）
  GROUP BY 分组列          ← 分堆
  HAVING 堆条件            ← 筛【堆】（可选）
  ORDER BY 别名 DESC
  LIMIT 行数;

【2.4 ⚠️⚠️ 铁律：SELECT 后面只放【分组列】和【聚合函数】】
  ❌ SELECT SUM(销售额), COUNT(*) FROM 订单 GROUP BY 类别
     → 跑出来是 (4502.1, 20) —— 数字对，但【不知道是哪一类】！
     → 而且 SQLite【不报错】，照样给你数据

  ✅ SELECT 类别, SUM(销售额), COUNT(*) FROM 订单 GROUP BY 类别

  【自查动作】写完带 GROUP BY 的 SQL，回头看：
             SELECT 第一个位置是不是【分组列】？

【2.5 ⭐⭐ HAVING vs WHERE（面试必问）】
  ┌──────────┬────────────────┬──────────────────┐
  │          │ WHERE          │ HAVING           │
  ├──────────┼────────────────┼──────────────────┤
  │ 筛什么    │ 【行】（明细）  │ 【堆】（分组后）  │
  │ 写在哪    │ GROUP BY 前面  │ GROUP BY 后面     │
  │ 能用聚合吗│ ❌ 不能        │ ✅ 能             │
  └──────────┴────────────────┴──────────────────┘

  写错会报：misuse of aggregate: SUM()
  【口诀】WHERE 管分堆前，HAVING 管分堆后
  【一句话答案】"WHERE 在分组前筛行，HAVING 在分组后筛组，能用聚合函数"

  ⚠️ 可移植性：HAVING 里用【别名】（HAVING 总额 > 1000）SQLite 允许，
     但 MySQL 不允许 → 跨数据库安全写法：HAVING SUM(销售额) > 1000

【2.6 ⚠️ ORDER BY 不写方向 = 默认从小到大（最阴的坑）】
  ❌ ORDER BY 销售额合计 LIMIT 3        → 拿到【最低】3 个
  ✅ ORDER BY 销售额合计 DESC LIMIT 3   → 才是【最赚钱】3 个

  【铁律】"前N名/最赚钱/最高/降序" → 必须写 DESC
  【自查动作】写完 ORDER BY 问自己："我要最大的还是最小的？"

【2.7 ⚠️ ROUND 必须带第二个参数】
  ROUND(值)      → 四舍五入到【整数】（0 位小数）★ 这个坑犯了 2 次！
  ROUND(值, 2)   → 保留 2 位小数 ✅

  实测证据：ROUND(541.5) = 542.0 ｜ ROUND(541.5, 2) = 541.5
  【自查动作】写完 ROUND( 看【结尾三个字符】必须是 ", 2)"

【2.8 本课对账数据（可用来自查）】
  按类别汇总销售额：水果 4502.1 / 饮料 2298.2 / 零食 1206.8 / 蔬菜 141.5
  按类别单数：      水果 20 / 饮料 9 / 零食 7 / 蔬菜 4

                    广州 1506.7 / 未知 1080 / 上海 598.5

                    1月 12 / 2912.2 / 242.68

三、多表连接 JOIN（第 3 课）⭐⭐ 面试必问
────────────────────────────────────────

【3.1 为什么 JOIN：因为信息分表存放】
  订单表里【没有成本价】—— 成本是"商品属性"（11 条），
  订单是"交易记录"（40 条）。混在一张表里要重复写 40 遍。
  分开存叫【规范化】，是数据库设计的标准做法。

  比喻：两张 Excel 表 → 按"商品名称"这个共同列 → 拼成一张宽表

【3.2 语法模板（四段结构）】
  SELECT 表A.列1, 表B.列2, 聚合函数
  FROM 表A                                  ← 左表
  INNER JOIN 表B ON 表A.共同列 = 表B.共同列   ← 右表 + 按什么拼
  WHERE ...  GROUP BY ...  ORDER BY ...

  ⚠️ ON 是必须的！漏了 → 每行和每行都配对 → 40 × 11 = 440 行笛卡尔积
  ⚠️ 两张表有同名列时，必须写【表名.列名】（如 订单.商品名称）
     否则报 ambiguous column name（列名有歧义）

【3.3 ⭐⭐ INNER vs LEFT（面试必问，一句话答案）】
  INNER JOIN  只保留【两边都匹配上】的行
  LEFT  JOIN  保留【左表全部】行，右表匹配不上填 NULL

  【本单元数据实证】
    表【订单】40 行 ｜ 表【商品成本】11 行（故意少了薯片、矿泉水）
    INNER JOIN → 38 行（薯片、矿泉水那 2 笔被丢掉）
    LEFT  JOIN → 40 行（全部保留，那 2 行成本价显示 NULL）

  【判断用哪个】
    只算"有成本数据的商品"毛利润   → INNER JOIN
    检查"哪些商品缺成本数据"        → LEFT JOIN + WHERE 右表.列 IS NULL
    列出所有订单（不管有没有成本）  → LEFT JOIN

  【LEFT JOIN 最实用的场景：找缺失数据】
    SELECT DISTINCT 订单.商品名称
    FROM 订单
    LEFT JOIN 商品成本 ON 订单.商品名称 = 商品成本.商品名称
    WHERE 商品成本.商品名称 IS NULL
    → 结果：矿泉水、薯片
    → 这叫【数据完整性检查】，真实工作非常常用

【3.4 用 JOIN 算毛利润】
  SELECT 订单.商品名称,
         ROUND(SUM(订单.销售额), 2) AS 销售额,
         ROUND(SUM(订单.数量 * 商品成本.成本价), 2) AS 总成本,
         ROUND(SUM(订单.销售额 - 订单.数量 * 商品成本.成本价), 2) AS 毛利润
  FROM 订单
  INNER JOIN 商品成本 ON 订单.商品名称 = 商品成本.商品名称
  GROUP BY 订单.商品名称
  ORDER BY 毛利润 DESC;

  ⚠️ 乘法要写在 SUM() 【里面】：
     ✅ SUM(数量 * 成本价)        先算每笔的成本再求和
     ❌ SUM(数量) * SUM(成本价)   两个总和相乘 —— 没有业务意义

  【对账数据】
    樱桃 972.0 / 咖啡 806.0 / 西瓜 313.5 / 巧克力 248.0 / 饼干 126.0
    香蕉 80.3 / 苹果 51.3 / 黄瓜 31.2 / 白菜 23.0 / 可乐 21.6 / 西红柿 14.4
    毛利润总额 2687.3（11 个商品）

    按供应商：山野果园 1023.3 / 云南豆业 806.0 / 海南瓜田 393.8 /
              甜心食品 374.0 / 绿野蔬菜 68.6 / 清爽饮料 21.6
    按类别：  水果 1425.1 / 饮料 842.0 / 零食 366.0 / 蔬菜 54.2（修复前）

【3.5 ⚠️⚠️ JOIN 最危险的陷阱：行数变多，数字虚高】
  若右表对同一个键有【多行】→ 左表 1 行变 N 行 → SUM 被重复计算
  例：樱桃 1 笔订单 1140 元，成本表有 2 条樱桃记录
      → JOIN 后樱桃出现 2 次 → SUM(销售额) = 2280 ❌（虚高一倍）

  【铁律】JOIN 之后，先跑 COUNT(*) 看行数合不合理，再算数字
  （本单元成本表设计成"每商品 1 行"，所以安全；但真实数据常有这个坑）

【3.6 UNION ALL（上下拼结果，不是左右拼）】
  SELECT 'A' AS 类型, COUNT(*) AS 行数 FROM 表1 ...
  UNION ALL
  SELECT 'B', COUNT(*) FROM 表2 ...
  → 结果上下排列
  ⚠️ 上下两段的列数要一样；列名以第一段为准
  ⚠️ JOIN 是【左右】拼宽；UNION ALL 是【上下】拼长 —— 完全不同

【3.7 UPDATE（改数据）⚠️ 安全铁律】
  语法：UPDATE 表名 SET 列名 = '新值' WHERE 条件
  ① 【必须先查后改】—— 先 SELECT 确认要改哪几行，再动手
  ② 【绝不能忘 WHERE】—— 不写会改【全表】！
     实测：UPDATE 订单 SET 类别='零食'  →  40 行全变成"零食"，不可恢复
  ③ 【必须 commit】—— Python 里改完要 conn.commit()，否则程序一关就白改

【3.8 pandas.read_sql() 打通 Python】
  import pandas as pd
  df = pd.read_sql("""SELECT ...""", conn)   ← 传【conn】，不是 cursor
  print(df.head())
  print(df["毛利润"].sum())

  【分工口诀】SQL 取数 → Pandas 分析 → Matplotlib 出图
  read_csv() 读【文件】 ｜ read_sql() 读【数据库】（真实工作更常用）
  ⚠️ 不要用 Pandas 读整张千万行的表（内存会爆）—— 该用 SQL 先筛/聚合

四、数据质量检查（本单元新增维度）⭐
────────────────────────────────────────

【4.1 新函数】
  COUNT(DISTINCT 列)         数"有几种不同的值"
     COUNT(类别)          → 数行数（重复也算）= 4
     COUNT(DISTINCT 类别)  → 数有几种值     = 2
  GROUP_CONCAT(DISTINCT 列)  把多个值拼成字符串（看是哪几种）
     GROUP_CONCAT(类别)          → 零食,零食,水果,零食
     GROUP_CONCAT(DISTINCT 类别) → 零食,水果
  ⚠️ GROUP_CONCAT 是 SQLite/MySQL 的；PostgreSQL 叫 STRING_AGG

【4.2 新检查模式：同一实体被标成多个值】
  SELECT 商品名称,
         COUNT(DISTINCT 类别) AS 类别数,
         GROUP_CONCAT(DISTINCT 类别) AS 类别列表
  FROM 订单
  GROUP BY 商品名称
  HAVING COUNT(DISTINCT 类别) > 1;

  换个列就能查别的问题：
    查"订单编号重复"：GROUP BY 订单编号 HAVING COUNT(*) > 1
    查"城市写法不一致"：GROUP BY 商品名称 HAVING COUNT(DISTINCT 城市) > 1

【4.3 ⭐ 本单元的真实发现（重要！）】
  查出：**巧克力** 同时出现在「零食」和「水果」两个类别里

  具体哪一笔：
    ORD0011 | 巧克力 | 零食 | 25.0 |  3
    ORD0024 | 巧克力 | 零食 | 25.0 | 19
    ORD0029 | 巧克力 | 水果 | 25.0 |  1   ← ⚠️ 这一笔错标了
    ORD0044 | 巧克力 | 零食 | 25.0 |  8
  （单价全是 25.0 → 同一个商品 → ORD0029 标错了）

  【为什么重要】这是你第 6 周数据清洗【漏掉】的一类检查！

  你原来的"五件套"：
    df.isnull().sum()          缺失值
    df.duplicated().sum()      重复行
    df["类别"].unique()        多余空格
    df["数量"].min()           负数量 / 0 单价
    pd.to_datetime()           日期格式

  ⭐ 新增【第六件：一致性检查】
    df.groupby("商品名称")["类别"].nunique() > 1
    （nunique() 就是 Pandas 版的 COUNT(DISTINCT)）

  【修复的代价是真实的】
    巧克力那笔：销售额 25.0 - 数量1 × 成本17.0 = 毛利润 8.0
    → 这 8.0 被算进了「水果」而不是「零食」
    修复前：水果 1425.1 / 零食 366.0
    修复后：水果 1417.1 / 零食 374.0   ← 各错了 8.0
    （你第 6 周报告的「水果 4502.1」「零食 1206.8」也受同一个错误影响）

五、本单元避坑手册（14 个坑，按类型分组）
────────────────────────────────────────

【类型 1：拼写 / 字符类】（跑一遍就能发现，但仍反复犯）
  坑 1：表名错 —— 写"订单表"，实际叫【订单】
        → 家族史：uft-8 / --online / tow / form / **订单表**
  坑 2：关键字拼错 —— DSEC（应 DESC）
        → 家族史同上（都是字母顺序颠倒）
  坑 3：全角标点 —— ，！（）混进语法位置
        → 报错诡异：no such column: a，b（三个列名被读成一个）
        → ⚠️ 区分：字符串/注释里的中文标点【没问题】，只有分隔代码的必须半角

【类型 2：结构类】
  坑 4：括号没闭合 —— round(avg(销售额,2)  ← 左括号 4 个右括号 3 个
  坑 5：ROUND 漏第二参数 —— ROUND(值) 只写一个参数 = 四舍五入到整数
        → ⚠️⚠️ 这个坑犯了【2 次】（第 2 课讲过，第 3 课又犯）
        → 动作：写完看结尾三个字符必须是 ", 2)"
  坑 6：SQL 写在三引号【外面】 —— 整个文件 SyntaxError

【类型 3：逻辑类】（⚠️ 不报错，但结果错 —— 最危险）
  坑 7：SELECT 忘了放【分组列】 —— 数字对，但不知道是哪一类
        → 自查：SELECT 第一个位置是不是分组列？
  坑 8：ORDER BY 不写方向 —— 默认从小到大，以为取"前3名"实际取"倒数前3"
        → 自查：问"我要最大的还是最小的？"
  坑 9：题目说"升序"却写 DESC —— 漏读要求（"半份作业"老毛病）
        → 自查：写完回头看题目逐项打勾（要哪几列/什么条件/怎么排）
  坑 10：题目要求 DISTINCT 却没写 —— 本例恰好结果一样，换个数据就露馅
  坑 11：JOIN 漏写 ON —— 笛卡尔积（440 行垃圾数据）
  坑 12：JOIN 后行数变多没察觉 —— SUM 被重复计算（右表有重复键时）

【类型 4：安全类】
  坑 13：UPDATE 忘了 WHERE —— 改全表！实测 40 行类别全变成"零食"，不可恢复
        → 铁律：先查后改 + 绝不能忘 WHERE
  坑 14：改完数据忘了 commit —— 改动只在内存，程序一关就白改

【⭐ 一个重要统计：14 个坑里，5 个不报错】
  不报错的：坑 7（缺分组列）、8（排序方向）、9（漏读要求）、
            10（缺 DISTINCT）、12（JOIN 行数）
  → **"能跑通" ≠ "结果对"** —— 这是本单元最值钱的一条

【⭐ 验证方法（比技能更重要）】
  ① 【交叉验证】同一个查询在两处跑出不同数字 → 必有一处错
     实例：题2 西瓜 313.5 vs 题10 西瓜 314.0
     （这正是你第 6 周做过的事：Pandas 算 167.6，SQL 再验一遍）
  ② 【不只看 head】head() 只能看大概；验证要看全量或汇总数
     实例：题 10 看 head 5 行只有 1 行错，全量 11 行里 6 行错
  ③ 【对账要看数字】跑完不能只看"有没有报错"，还要看"数字对不对"

六、离线自测题（先自己答，再看答案）
────────────────────────────────────────
  Q1. SELECT 的书写顺序是什么？
  Q2. SQL 里"等于"怎么写？文字值用什么引号？
  Q3. WHERE 里同时有 AND 和 OR，为什么建议加括号？
  Q4. COUNT(*) 和 COUNT(列) 有什么区别？
  Q5. GROUP BY 之后，SELECT 后面只能放哪两种东西？
  Q6. WHERE 和 HAVING 的区别？（一句话）
  Q7. ORDER BY 不写 ASC/DESC 时，默认是哪个方向？
  Q8. ROUND(541.5) 和 ROUND(541.5, 2) 分别得到什么？
  Q9. INNER JOIN 和 LEFT JOIN 的区别？（一句话）
  Q10. JOIN 时为什么要在列名前写"表名."？
  Q11. JOIN 漏写 ON 会发生什么？
  Q12. 怎么用 LEFT JOIN 找出"主表有、附表没有"的数据？
  Q13. SUM(数量 * 成本价) 和 SUM(数量) * SUM(成本价) 有什么区别？
  Q14. UPDATE 不写 WHERE 会有什么后果？
  Q15. 改动数据后忘了 commit 会怎样？
  Q16. COUNT(DISTINCT 类别) 和 COUNT(类别) 的区别？
  Q17. 怎么查"同一个商品被标成了多个类别"？
  Q18. pandas.read_sql() 第二个参数传什么？
  Q19. 为什么说"能跑通不等于结果对"？举一个本单元的例子。
  Q20. 什么是"交叉验证"？它为什么有用？

  【答案】
  A1. SELECT → FROM → WHERE → ORDER BY → LIMIT
  A2. 用一个 =（不是 ==）；文字值必须用单引号 '文字'。
  A3. 因为 AND 比 OR 先算。不加括号时
      A OR B AND C 会被理解成 A OR (B AND C)，结果可能多出很多行。
  A4. COUNT(*) 数所有行；COUNT(列) 只数该列【不为空】的行。
  A5. 只能放【分组列】和【聚合函数】。放普通列会得到无语义的结果
      （SQLite 不报错，随便挑一个值）。
  A6. WHERE 在分组【前】筛【行】，不能用聚合函数；
      HAVING 在分组【后】筛【组】，能用聚合函数。
  A7. 默认 ASC（从小到大）。
  A8. ROUND(541.5) = 542.0（四舍五入到整数）；
      ROUND(541.5, 2) = 541.5（保留 2 位小数）。
  A9. INNER JOIN 只保留两边都匹配上的行；
      LEFT JOIN 保留左表全部行，右表匹配不上的填 NULL。
  A10. 因为两张表有同名列，不写表名 SQL 分不清是哪张表的
       （会报 ambiguous column name）。
  A11. 会变成【笛卡尔积】—— 每一行和每一行都配对。
       例：40 × 11 = 440 行垃圾数据。
  A12. LEFT JOIN 之后用 WHERE 右表.列 IS NULL 筛出来。
       （这就是"数据完整性检查"）
  A13. SUM(数量 * 成本价) 先算每笔成本再求和 ✅ 正确；
       SUM(数量) * SUM(成本价) 是把两个总和相乘 ❌ 没有业务意义。
  A14. 会把【全表】那一列都改掉。实测 40 行的类别全变成"零食"，
       数据被破坏且通常不可恢复。
  A15. 改动只在内存里，程序一关就没了（没真正写入数据库文件）。
  A16. COUNT(类别) 数的是【行数】（重复也算）；
       COUNT(DISTINCT 类别) 数的是【有几种不同的值】。
  A17. SELECT 商品名称, COUNT(DISTINCT 类别)
       FROM 订单 GROUP BY 商品名称
       HAVING COUNT(DISTINCT 类别) > 1
       （本单元查出的是"巧克力"）
  A18. 传数据库【连接对象 conn】，不是 cursor。
  A19. 因为很多错误不报错，只是数字悄悄错了。例：
       题 2 的 ROUND 漏参数 → 西瓜总成本 541.5 被算成 542.0；
       缺分组列 → 数字对但没有类别名。
  A20. 用两种方法算同一个数，看结果是否一致。
       不一致就说明有一处错了 —— 这是最有效的自查手段之一。

────────────────────────────────────────
七、本单元口诀总集
────────────────────────────────────────

【基础查询】
  选从行筛排序限量，顺序一乱就报错；
  等于就是一个 =，文字要用单引号；
  AND 咬得紧，OR 松；要改先后，上括号。

【聚合与分组】
  聚合五兄弟：COUNT 数、SUM 加、AVG 平均、MAX/MIN 找两头；
  GROUP BY 来分堆，SELECT 只放【分组列 + 聚合函数】；
  不报错 ≠ 对，混进普通列最危险；
  分组完顺序是乱的，要顺序必须 ORDER BY；
  WHERE 管分堆前，HAVING 管分堆后；
  ORDER BY 不写方向，默认从小到大；要"前N名"就写 DESC；
  ROUND 结尾看三个字符：必须是 ", 2)"。

【多表连接】
  信息分开放，需要就连表；JOIN 要写 ON，连接靠共同列；
  两张同名列，前面加表名；
  INNER 配得上才留，LEFT 左表全都留，配不上填 NULL；
  LEFT JOIN + IS NULL，专找"主表有、附表没有"的；
  乘法写在 SUM 里面，别把两个总和乘；
  ⚠️ JOIN 后先看行数，再看数字对不对；
  UPDATE 先查后改，绝不能忘 WHERE；改完必须 commit。

【数据质量】
  COUNT(DISTINCT) 数种类，GROUP_CONCAT 看是哪几种；
  同一实体多个值 → 一致性检查（清洗第六件）；
  改了数据，同一句 SQL 的结果就变了 —— 报告要注明数据时间。

【验证心法】⭐ 本单元最重要
  能跑通不等于结果对 —— 跑完还得看数字；
  head 只够看大概，验证要看全量或汇总；
  同一个查询两处跑出不同数 → 一定有一处错了（交叉验证）。
