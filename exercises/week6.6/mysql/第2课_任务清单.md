## 二、本课核心知识：SQLite vs MySQL 到底差在哪

你在第 6.5 单元学的是 SQLite（Python 自带，零配置）。
MySQL 是**服务端数据库**，是这个行业里更常见的那个。真正的差异只有 4 处：

### 差异 1：连接方式（这是最本质的差别）

```
SQLite                          MySQL
──────────────────────────────  ──────────────────────────────────
sqlite3.connect("销售.db")       pymysql.connect(
一个【文件】                          host="127.0.0.1", port=3306,
不需要账号密码                        user="root", password="***",
                                    database="销售_db")
                                → 一个【服务】，要地址 + 账号 + 密码
```

💡 **比喻**：
- SQLite = **一个 Excel 文件**，谁拿到文件谁能看，没有门卫
- MySQL = **一个仓库**，门口有门卫（用户/密码），
  还有权限本（谁能进哪个库、能干什么）

**这就是为什么 JD 里都写 MySQL**——真实项目是多人共用一个数据库，
必须有服务端和权限体系。你一个人用 SQLite 没问题，
但**一进公司就必须会 MySQL**。

⚠️ **一个真实的后果**：密码不能写进代码。
所以我们用 `db_config.py` + `.gitignore`（**已经加好了**）。
第 7-11 周第 3 课会学更规范的 `.env` 做法。

### 差异 2：类型严格程度 ⭐（本课最有价值的体会）

```
SQLite 是【动态类型】：类型只是建议，存字符串进去也不报错
MySQL  是【严格类型】：说好是 INT，你塞个 'abc' 就报错
```

所以 MySQL 建表时必须写**长度和精度**：

| SQLite 里写的 | MySQL 该写 | 为什么 |
|---|---|---|
| `TEXT` | `VARCHAR(20)` | 短文本要指定最大长度 |
| `INTEGER` | `INT` | 基本一样 |
| `REAL` | `DECIMAL(10,2)` | ⚠️ **钱必须用 DECIMAL** |
| `'2026-01-01'`（文本）| `DATE` | 日期有专门类型 |

⚠️⚠️ **为什么钱要用 DECIMAL 而不是 FLOAT**（面试爱问）：
浮点数存 0.1 是**近似值**，累加会出 `0.30000000000000004` 这种鬼东西。
`DECIMAL` 是精确定点数，专门存钱。
（SQLite 里你用的是 REAL 就是浮点——那是 SQLite 的简化。）

⭐ **这一条会在 `03_交叉验证.py` 里亲眼看到**：
同一个日期，SQLite 返回的是**字符串** `'2026-01-01'`，
MySQL 返回的是**日期对象** `datetime.date(2026, 1, 1)`。
同一个 `ROUND()`，SQLite 返回 **float**，MySQL 返回 **Decimal**。
**这些都不是错**——是 MySQL 更严谨。

### 差异 3：ONLY_FULL_GROUP_BY（MySQL 会拦住你）

回忆你第 6.5 单元的笔记原话：

> 『SELECT 里只能放**分组列 + 聚合函数**（放了别的列不报错，但结果无意义）』

⚠️ **那是 SQLite 的行为。** MySQL 8 默认开启了 `ONLY_FULL_GROUP_BY` 模式，
对这种 SQL **直接拒绝执行**。

`03_交叉验证.py` 最后专门跑了这条对比，**你去看两边分别是什么反应**。
→ 这说明：**SQLite 对你的错误很宽容，MySQL 不宽容。**
**别把 SQLite 的宽容当成"我写对了"。**

### 差异 4：参数占位符（最容易写错的细节）

```python
# SQLite（第 6.5 单元）        MySQL（本课）
cur.execute(sql, ("上海",))    cur.execute(sql, ("上海",))
                 ↑ ?                          ↑ %s
```

⚠️ **`?` 换成 `%s`**，这是 `pymysql` 的规定。写错了会报
`not enough arguments for format string` 之类的怪错。

## 五、避坑预告

| # | 坑 | 症状 | 解药 |
|---|-----|------|------|
| 1 | **只装 pymysql 没装 cryptography** | 认证失败，报错很难懂 | `pip install pymysql cryptography` |
| 2 | **占位符写成 `?`** | `not enough arguments for format string` | MySQL 要用 **`%s`** |
| 3 | **单参数没写成元组** | 报错或行为诡异 | 写成 `("TEST0001",)` —— **逗号不能少** |
| 4 | **忘了 `commit()`** | 程序里查得到，关掉就没了 | 增删改都要 commit（查询不用）|
| 5 | **`UPDATE` 忘了 `WHERE`** | 全表被改 | 先 `SELECT` 看一眼，改完看 `rowcount` |
| 6 | **字符集不是 utf8mb4** | 中文变 `???` 或乱码 | 建库建表都写 `DEFAULT CHARSET = utf8mb4` |
| 7 | **列顺序对不上** | 数据串列（城市跑到月份里）| 迁移时列名列表顺序 == 建表顺序 |
| 8 | **金额用了 FLOAT** | 加总出现 `xxx.00000001` | 钱用 `DECIMAL(10,2)` |
| 9 | **全角标点** | 又是你那个老坑 | SQL 里的逗号/括号必须**半角** |
| 10 | **中英文引号混用** | 反引号 `` ` `` 和单引号 `'` 搞混 | 反引号包**名字**，单引号包**值** |

⚠️ **第 9 条要特别小心**：本课 SQL 写得比第 6.5 单元长（一列一行），
**全角逗号混进去的几率更高**。而且 MySQL 的报错信息不如 SQLite 友好。
→ **动作**：写 SQL 时把输入法切到英文；写一句跑一句，别一次写完再跑。

## 七、这一课值多少（诚实的评估）
